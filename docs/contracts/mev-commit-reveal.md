# MEV Commit-Reveal Escrow & Upgrade Guide

This document specifies the StellarRoute router contract's commit-reveal MEV protection scheme (`crates/contracts/src/router.rs`), the exact canonical XDR commitment hash pre-image, escrow lifecycle, and upgrade/migration steps for existing deployments.

---

## 1. Protocol Lifecycle

When `MevConfig` is configured and `params.amount_in >= mev_config.commitment_required_above`, direct calls to `execute_swap` fail with `ContractError::CommitmentRequired`. Callers must execute a two-phase commit-reveal swap:

1. **Commit & Escrow (`commit_swap`)**
   - Signature:
     ```rust
     pub fn commit_swap(
         e: Env,
         sender: Address,
         commitment_hash: BytesN<32>,
         deposit_asset: Asset,
         deposit_amount: i128,
     ) -> Result<(), ContractError>
     ```
   - Requires `sender.require_auth()` and an unpaused router.
   - Rejects `deposit_amount <= 0`, zeroed `commitment_hash` (`[0u8; 32]`), unallowlisted `deposit_asset` (when the allowlist is active, i.e. `token_count > 0`), and duplicate `(sender, commitment_hash)` entries (`ContractError::InvalidAmount`).
   - Transfers `deposit_amount` of `deposit_asset` from `sender` into the router contract (`e.current_contract_address()`).
   - Stores `CommitmentData` in **persistent** storage under `StorageKey::Commitment(sender, commitment_hash)` with `created_at = current_ledger` and `expires_at = current_ledger + mev_config.rate_limit_window_ledgers`.

2. **Minimum Reveal Delay (`min_reveal_delay_ledgers`)**
   - `configure_mev` enforces `1 <= min_reveal_delay_ledgers <= rate_limit_window_ledgers`.
   - Any `reveal_and_execute` submitted at `current_ledger < created_at + min_reveal_delay_ledgers` (including in the same ledger as `commit_swap`) is rejected with `ContractError::ExecutionTooEarly`.

3. **Reveal & Execute (`reveal_and_execute`)**
   - Signature:
     ```rust
     pub fn reveal_and_execute(
         e: Env,
         sender: Address,
         params: SwapParams,
         salt: BytesN<32>,
     ) -> Result<SwapResult, ContractError>
     ```
   - Recomputes `commitment_hash` over `(sender, params, salt)` using canonical Soroban XDR (see Section 2).
   - Looks up `StorageKey::Commitment(sender, commitment_hash)` (`ContractError::CommitmentNotFound` if any field of `sender`, `params`, or `salt` differs).
   - Enforces `created_at + min_reveal_delay_ledgers <= current_ledger <= expires_at`.
   - Enforces `params.route.hops[0].source == commitment.deposit_asset` and `params.amount_in == commitment.deposit_amount` (`ContractError::InvalidReveal` on mismatch; Soroban atomically rolls back state so the escrowed deposit remains intact).
   - Deletes the commitment entry and executes the route funded directly from the router contract's escrowed balance (without pulling a second input transfer from `sender`).

4. **Expiry Refund (`reclaim_commitment`)**
   - Signature:
     ```rust
     pub fn reclaim_commitment(
         e: Env,
         sender: Address,
         commitment_hash: BytesN<32>,
     ) -> Result<i128, ContractError>
     ```
   - Requires `sender.require_auth()` and `current_ledger > commitment.expires_at` (`ContractError::ExecutionTooEarly` if not yet expired).
   - Deletes the commitment record and transfers `commitment.deposit_amount` of `commitment.deposit_asset` from the router contract back to `sender`.
   - Intentionally allowed even while the router is paused so users can always recover expired escrowed funds.

## 2. Exact Commitment Hash Pre-Image Specification

The commitment hash is the SHA-256 digest of the concatenated canonical RFC 4506 / Soroban `ScVal` XDR byte encodings of `sender`, `params`, and `salt`:

```text
preimage        = XDR(sender : Address) || XDR(params : SwapParams) || XDR(salt : BytesN<32>)
commitment_hash = SHA-256(preimage)
```

In Soroban Rust (`soroban_sdk::xdr::ToXdr`):

```rust
let mut preimage = Bytes::new(&e);
preimage.append(&sender.clone().to_xdr(&e));
preimage.append(&params.clone().to_xdr(&e));
preimage.append(&salt.clone().to_xdr(&e));
let commitment_hash: BytesN<32> = e.crypto().sha256(&preimage).into();
```

Each component is a self-delimiting `ScVal` XDR value (prefix-free, making concatenation unambiguous and collision-free):

1. **`XDR(sender)`** — `ScVal::Address(ScAddress)` encoding the committing account or contract address.
2. **`XDR(params)`** — `ScVal::Map` generated by `#[contracttype]` for `SwapParams`, with keys sorted lexicographically by symbol name:
   - `amount_in` (`ScVal::I128`)
   - `deadline` (`ScVal::U64`)
   - `max_execution_spread_bps` (`ScVal::U32`)
   - `max_price_impact_bps` (`ScVal::U32`)
   - `min_amount_out` (`ScVal::I128`)
   - `not_before` (`ScVal::U64`)
   - `recipient` (`ScVal::Address`)
   - `route` (`ScVal::Map` for `Route`: `estimated_output`, `expires_at`, `hops` vector of `RouteHop { destination, pool, pool_type, source }`, and `min_output`)
3. **`XDR(salt)`** — `ScVal::Bytes(ScBytes)` of length 32 containing the caller's random 32-byte salt.

Integrators and wallets can also query the read-only contract helper `compute_commitment_hash(sender, params, salt) -> BytesN<32>` via Soroban RPC simulation to obtain or verify the exact digest before submitting `commit_swap`.

## 3. Storage & TTL Guarantees

`CommitmentData` is stored in **Persistent** storage (`StorageKey::Commitment(Address, BytesN<32>)`) with TTL extended to `max(rate_limit_window_ledgers, 30 * DAY_IN_LEDGERS)`. Unlike `temporary()` storage—which permanently deletes entries upon TTL expiration and cannot be restored—`persistent()` storage ensures that expired commitment records remain readable (or restorable via Stellar archival restoration) until `reclaim_commitment` refunds the user's escrowed tokens.

## 4. Upgrade & Migration Notes for Existing Deployments

This change modifies on-chain ABI and storage types (`MevConfig`, `CommitmentData`, `StorageKey::Commitment`, and `commit_swap`):

1. **Pre-Upgrade Drain / Window Wait:**
   - Legacy commitments created prior to this upgrade did not escrow tokens and lived in `temporary()` storage under `StorageKey::Commitment(BytesN<32>)` with TTL `rate_limit_window_ledgers`.
   - Before executing the WASM upgrade (`propose_upgrade` / `execute_upgrade` or governance `ProposalAction::Upgrade`), either pause MEV commits or wait `rate_limit_window_ledgers` ledgers after the upgrade is scheduled so any in-flight legacy commitments are revealed or naturally expire. Because legacy commitments held zero escrowed tokens, no user funds are at risk in legacy temporary entries.
2. **Re-Initializing `MevConfig` After Upgrade:**
   - `MevConfig` adds `pub min_reveal_delay_ledgers: u32`. If `StorageKey::MevConfig` in instance storage holds a serialized legacy 5-field `MevConfig`, Soroban `#[contracttype]` map deserialization will fail until rewritten.
   - Immediately after `execute_upgrade` (ideally batched right after upgrade execution by admin/multisig), call `configure_mev` with the updated 6-field `MevConfig` (setting `1 <= min_reveal_delay_ledgers <= rate_limit_window_ledgers`, e.g. `1` or `2` ledgers).
3. **Client / SDK Updates:**
   - Update callers of `commit_swap` to pass `(sender, commitment_hash, deposit_asset, deposit_amount)` and ensure `sender` holds/authorizes `deposit_amount` of `deposit_asset`.
   - Replace legacy 4-field `(amount_in || min_amount_out || deadline || salt)` hashing with `SHA-256(XDR(sender) || XDR(params) || XDR(salt))` (or simulate `compute_commitment_hash`).
   - Wait at least `min_reveal_delay_ledgers` ledgers before submitting `reveal_and_execute`, and expose `reclaim_commitment(sender, commitment_hash)` for expired commitments.
